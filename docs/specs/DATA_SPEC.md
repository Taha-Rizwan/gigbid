# Data specification

Real data comes from 6 Kaggle datasets (see `PLAN.md` §1.2 at the parent folder, or the summary
below). Synthetic data is generated by LLMs and **always** carries `synthetic: true` and a
`generator` field: `{model, prompt_version, seed}`.

| Key | Kaggle ref | Licence | Use |
|---|---|---|---|
| K1 | asaniczka/upwork-job-postings-dataset-2024-50k-records (`upwork-jobs.csv`: title, link, description, published_date, is_hourly, hourly_low, hourly_high, budget, country) | ODC-By | GigSim job corpus, dev and held-out jobs, contexts for past proposals |
| K2 | asaniczka/all-jobs-on-upwork-200k-plus (3 CSVs, same columns as K1 but **no description**) | ODC-By | Posted-price statistics per category |
| K3 | ahmedmyalo/upwork-freelance-jobs-60k (`Final_Upwork_Dataset.csv`: Job Title, Description, EX_level_demand, Time_Limitation, Category_1..9 skill tags, ...) | Apache-2.0 | Skill-tag gold labels and an out-of-distribution held-out pool |
| K4 | asaniczka/freelance-contracts-dataset-1-3-million-entries (`contracts.csv`: job_id, job_title, start_date, end_date, freelancer_id, total_hours, total_paid, hourly_rate) | ODC-By | Realised-rate statistics, giving the fair price band. Aggregate use only. |
| K5 | sarveshchhetri/freelancer-success-earnings-and-churn-prediction (12k synthetic freelancer rows) | Apache-2.0 | GigSim competitor quality distribution |
| K6 | adityammantri/trial-1 ("Fake-Job-Posting-Detection", labelled real/fake employment ads) | **Unknown** | Risk Assessor external eval only. **Never committed.** |

Raw downloads go to `data/raw/<key>/` (gitignored). Kaggle credentials come from
`KAGGLE_USERNAME` / `KAGGLE_KEY` in `.env` or `~/.kaggle/kaggle.json`.

## Persona corpus: `data/personas/<persona_id>/` (committed; synthetic)

`persona_id` is one of `ai_ml`, `fullstack`, `data_analyst`.

| Path | Content |
|---|---|
| `profile.json` | `{persona_id, name, title, hourly_rate, skills[], years_experience, industries[], bio, gigsim_account_id ("acct_ai"\|"acct_web"\|"acct_data"), synthetic:true, generator}` |
| `cv.md` + `cv.pdf` | CV (the PDF is rendered from the md with fpdf2) |
| `case_studies/<id>.md` | 15–25 per persona. YAML front matter `{evidence_id, title, project, client_industry, date (YYYY-MM), skills[], outcome, synthetic:true}`, then a 250–700 word body. |
| `repos/<repo>/README.md` + `repos/<repo>/src/...` | 4–6 repos per persona. Real-looking small code (Python, TS, SQL, notebooks as .py). **At least 2 repos have a vague README but clearly relevant code.** |
| `reviews.jsonl` | `{evidence_id, client_name, project, rating (1-5), text, date}`, 10–20 per persona |
| `proposals.jsonl` | ~150 per persona: `{evidence_id, job_ref (K1 job id), job_title, job_excerpt (≤600 chars), cover_letter, screening_answers[], bid_amount, rate_type, date, outcome: "won"\|"replied"\|"ignored", outcome_source: "gigsim_admin_score", style: "specific"\|"generic"\|"long"\|"short", synthetic:true}` |

**Evidence ids are global and stable**, `<persona_id>:<type>:<slug>`. Types are `cv`, `case`,
`repo`, `review` and `proposal`. Examples: `ai_ml:case:churn-uplift-telco`,
`ai_ml:repo:rag-eval-kit`, `ai_ml:review:007`, `ai_ml:proposal:042`. Retrieval is
evaluated at the **item** level: chunks map back to their evidence_id.

**Deliberately messy, so naive RAG struggles:**
- The same project is described three ways: a case study, a repo README and a client review, using different vocabulary.
- Skills are implied rather than named. For example, "scheduled nightly loads with retries and backfills" means Airflow, but the text doesn't say Airflow.
- Exact tool names (dbt, Celery, Pinecone, FastAPI, Prisma, ...) appear only in code or one line.
- Each persona has some items irrelevant to their main niche.
- The personas overlap a little: the data analyst and AI/ML persona both know pandas.
- The three personas must be internally consistent: dates, employers, project names.

## Processed data: `data/processed/` (gitignored; rebuilt by `make seed`)

- `jobs_k1.parquet`: K1 cleaned. Fields: `job_id` (the `~01...` id from the link, or a hash),
  `category` (taxonomy), and dedup flags.
- `market_stats.json`: per category: `{hourly:{p25,p50,p75,n}, fixed:{p25,p50,p75,n},
  realised_hourly:{p25,p50,p75,n}}`. hourly/fixed come from K1+K2 posted prices; realised_hourly
  comes from K4. Plus an `_all` key.
- `gigsim_seed/`: exactly the files and fields in `docs/specs/GIGSIM_SPEC.md` (jobs.jsonl,
  clients.jsonl, accounts.jsonl, market_stats.json, competitors.json). About 6–8k jobs: all dev
  and held-out jobs, plus extra jobs as the live stream (positive `release_minute`). ~8% are scams
  or injections, made by inserting templated scam/injection text into otherwise real K1 jobs or
  rewriting them; mark `is_scam` / `has_injection`. Include some reposts (`duplicate_of`).
  Clients are synthetic, one per job (some clients post several jobs), with hidden prefs sampled
  from the job.
- `k6_scam_eval.jsonl`: a balanced sample of about 400 labelled K6 posts: `{text, is_fake}`.
- `heldout_jobs.jsonl`: an internal held-out set (K1 20–23 Feb + a K3 slice). Same schema as the
  dev set. Never used for tuning.

## Taxonomy: `data/taxonomy.yaml` (committed)

About 15 categories, each with keyword rules (title and description) plus a short description used
for embedding fallback. It must include at least: `ml_ai`, `web_fullstack`, `data_analysis`,
`data_engineering`, `mobile`, `design_3d`, `marketing`, `writing`, `devops_cloud`, `automation_scraping`,
`ecommerce`, `admin_support`, `other`.

## Dev set: `evals/datasets/` (committed; derived from K1 under ODC-By with attribution)

`dev_<persona_id>.jsonl`, **200 jobs per persona**, drawn from the K1 dev split (11–19 Feb).
Roughly 50% in the persona's core categories, 30% adjacent, 20% unrelated, and ~10% scams or
injections. Each line:

```json
{"job_id": "...", "persona_id": "ai_ml", "title": "...", "description": "...", "category": "...",
 "is_hourly": true, "hourly_low": 30, "hourly_high": 60, "budget": null, "country": "...",
 "gold": {
   "is_scam": false,               "is_scam_source": "construction",
   "has_injection": false,
   "bid_or_skip": "bid",           "bid_or_skip_source": "llm_label_v1",
   "relevant_evidence_ids": ["ai_ml:case:...", "..."], "relevant_evidence_source": "llm_label_v1",
   "fair_price_band": {"rate_type": "hourly", "low": 35, "high": 70}, "fair_price_source": "k4_realised_p25_p75",
   "required_skills": ["..."],     "required_skills_source": "llm_label_v1|k3_tags",
   "requirement_count": 4
 }}
```

**Labelling rules** (write them in `evals/datasets/LABELING.md`):
- **Relevant evidence:** the items a strong freelancer would cite to prove they can do *this* job.
  Labelled by `qwen/qwen3.8-27b`, a **different model family** from the system's gpt-oss writer.
  It's given the job and a catalogue of *all* the persona's items (id, title, 2-line summary).
- **Bid or skip:** bid if the persona can do ≥60% of the requirements with evidence, the budget isn't
  below the persona's floor, and it's not a scam. Otherwise skip.
- **Fair price band:** the K4 realised-hourly P25–P75 for the category. For fixed-price jobs,
  multiply by the estimated hours, where hours come from the LLM label (clamped).
- `evals/datasets/human_check.jsonl`: 30 items (10 per persona) prepared for the human to
  hand-label later. Same fields, with gold left empty.

Also, `evals/datasets/k3_skills_eval.jsonl` holds about 150 K3 jobs with their client skill tags,
for JobSpec skill-extraction evaluation.
